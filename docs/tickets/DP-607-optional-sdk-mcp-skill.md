# DP-607 — Optional SDK, MCP, or agent skill after the HTTP contract is stable

Status: FUTURE
Milestone: M6 — open-source and release hardening / post-M4 client ecosystem
Depends on: DP-105 public schema, DP-402 read-only HTTP API, DP-403 OpenAPI and versioning policy; legal/publication gates remain prerequisites
Launch state: blocked until the stable API contract and owner decision exist; no client, MCP server, skill, or external publication is authorized here

## Problem

The repository's durable public boundary is the fail-closed public projection. A future
SDK, MCP server, or agent skill could make that boundary convenient, but it could also
freeze an unstable field vocabulary, expose private operational data, encourage an agent
to treat a candidate as a verdict, or create a second read path around review and
publication policy.

The API contract is not yet a stable release boundary: DP-105 must ratify the public
schema, DP-402 must define the read-only HTTP behavior, and DP-403 must publish and
version the OpenAPI description. A client or tool built before those gates would turn
an implementation detail into a promise.

## Outcome

Define a gated, optional client-ecosystem decision:

- **API first:** no SDK, MCP server, or agent skill is implemented or advertised before
  the stable HTTP/OpenAPI contract is accepted;
- choose at most one optional surface at a time, with a documented use case and owner;
- make every client a thin, read-only consumer of the same public API/projection;
- preserve provenance, correction/reply, temporal, and no-intent semantics;
- make client versioning, deprecation, licensing, security, and clean-clone behavior
  explicit; and
- permit “do not build” when the API contract or demand does not justify a client.

This ticket is a specification and decision gate, not an implementation or publication
authorization.

## Baseline and evidence limits

Current baseline:

- `web/README.md` expects a public projection generated by
  `dichiarazioni_pubbliche.public_projection`;
- the current operational projection identifier is `dichiarazioni-pubbliche-public-v2`;
- DP-105, DP-402, and DP-403 are still the owners of public schema, HTTP route, and
  OpenAPI/versioning decisions;
- no SDK, MCP server, agent skill, remote, or public API publication exists; and
- the repository's Apache-2.0 code license does not automatically license third-party
  client dependencies or public data.

No separate DP-601 baseline or W0R/W0P file was present in the current checkout. That
absence must be verified before any client work; no report or remote path is invented.

## Dependency and decision gate

The order is hard:

```text
DP-105 public schema compatibility
        -> DP-402 stable read-only HTTP routes
        -> DP-403 OpenAPI, examples, and deprecation policy
        -> M3 legal/privacy/rights and M6 release gates
        -> optional SDK OR MCP OR skill decision
```

A client may be prototyped against fixtures before the gate only when it is clearly
marked draft, local, read-only, and not published. It must not be called stable,
supported, public, or an API replacement. The owner must explicitly choose whether a
client is needed and which single surface, if any, is in scope.

## Scope

### 1. Shared client contract

Any selected client must consume the same versioned HTTP contract described by
DP-402/DP-403 and the DP-105 projection. It must:

- use stable opaque resource identifiers and documented pagination/cursors;
- honor ETag/freshness and contract-version behavior;
- expose only public-safe fields and documented error states;
- distinguish an unresolved/needs-more-evidence result from a stronger verdict;
- retain correction, right-of-reply, relation, and temporal semantics;
- never infer intent, speaker identity, evidence approval, or publication from a client
  response; and
- fail closed on an unknown contract, stale projection, malformed response, missing
  provenance, or incompatible major version.

Clients must not call PostgreSQL, a provider, a worker, an LLM, or a private filesystem
path. They must not provide arbitrary SQL, unrestricted search, raw transcript/evidence
bodies, or hidden write/admin operations.

### 2. Optional generated SDK

If the owner selects an SDK, it must be generated from the accepted OpenAPI document or
a deliberately maintained thin wrapper, with the source OpenAPI version recorded. The
first SDK must:

- support only the documented public `GET`/`HEAD` operations;
- use bounded timeouts, retries only for safe idempotent reads, and explicit pagination;
- preserve error/status semantics and contract-version rejection;
- contain no provider credentials, database access, publication action, or private
  Studio route;
- have generated/source license and notice records; and
- include compatibility tests against the DP-105 schema and the API contract fixtures.

An SDK is optional. A generated client must not force a breaking public API change or
become the source of truth for field names.

### 3. Optional MCP server

If the owner selects MCP, it must be a thin read-only adapter over the same HTTP API,
not a second data authority. Its tool surface must be small and explicit, for example
read manifest, read a bounded public resource, and read a public collection. It must:

- reject mutation, approval, evidence, publication, intake, and administrative tools;
- use the same bounded pagination, error, freshness, and contract-version rules;
- avoid arbitrary URL fetching, SQL, crawling, provider calls, and hidden search;
- label all responses with the public contract version and provenance limitations;
- apply rate/size/time bounds and safe logging; and
- be independently testable with a local mock HTTP server and the DP-602 CI matrix.

MCP is not a publication channel, agent authority, or way to make private projections
available. If the stable API cannot support a safe bounded tool, the correct result is
“do not build MCP.”

### 4. Optional agent skill or documentation package

If the owner selects an agent skill, it is an instruction/documentation surface that
links to the canonical API, manifest, OpenAPI document, and public method. It must:

- tell agents to read the contract rather than infer fields or URLs;
- preserve retrieval/approval/verification/publication distinctions;
- prohibit auto-approval, auto-publication, intent inference, biometric matching, and
  private-data access;
- use fictional examples and bounded requests; and
- include a version/fingerprint and an update/deprecation path.

A skill is not an autonomous reviewer, publisher, browser session, or replacement for
`SECURITY.md`, the public method, or human review.

## Non-goals

- implementing all three surfaces at once or committing to a language/runtime ecosystem;
- creating an SDK, MCP server, skill, registry package, or public documentation site in
  this ticket;
- a paid, authenticated, realtime, bulk, BYOK, or managed-quota API;
- public writes, intake, correction submission, reply submission, evidence approval,
  Finding publication, or admin operations;
- calling an LLM/provider from a client or tool, or making a model the publication
  authority;
- exposing raw/canonical transcripts, evidence bodies, provider receipts, private
  replies, secrets, or operational database fields;
- whole-web search, arbitrary crawling, graph/vector infrastructure, or a new database;
- renaming the project/package or changing the public schema outside DP-105/DP-403;
  and
- creating a remote, release, tag, or external publication.

## Security, licensing, and versioning requirements

### Security and semantics

- default to public, read-only, unauthenticated behavior only where DP-402 explicitly
  defines it; never imply an API key or account contract;
- validate contract version, schema, content type, response size, timeout, and redirect
  behavior at the client boundary;
- never log request bodies containing private data, credentials, raw evidence, or
  provider prompts;
- treat missing/stale/incompatible projection data as blocked, not as an empty verified
  record;
- preserve no-auto-publication, no-intent, no-person-score, no-biometric, and private-by-
  default rules in docs, examples, generated code, and tests; and
- use a local mock/fake server for deterministic CI; no real provider or public remote
  is required.

### Licensing

- record the client implementation, generated-code source, dependencies, and any
  bundled examples in DP-603 with exact versions, license evidence, notices, and
  attribution;
- do not copy OpenAPI examples, schema text, or donor code beyond the applicable license
  or generate a client from an unreviewed third-party artifact;
- keep the Apache-2.0 code boundary separate from public data/content terms; and
- fail the release gate on unknown or incompatible dependency licensing.

### Versioning

- the public API major version is owned by DP-105/DP-403 and is not chosen by an SDK,
  MCP server, or skill;
- a client version is independent but must record the supported API range and generated
  source version;
- additive optional API changes may be consumed after contract tests pass; breaking
  field/route/meaning changes require a new API major and a client compatibility plan;
- deprecated endpoints follow DP-403's replacement and sunset policy; and
- a client must never silently reinterpret a removed field, enum, or resource as a
  stronger truth or publication state.

## Acceptance criteria

- [ ] **AC-607.1 — API-before-client gate:** No SDK, MCP server, or skill implementation
  is marked stable or published until DP-105, DP-402, and DP-403 close their contract
  gates and the owner selects one surface.
- [ ] **AC-607.2 — Single authority:** The selected client consumes the same HTTP API and
  DP-105 public schema, with no second database, projection, provider, or publication
  path.
- [ ] **AC-607.3 — Read-only behavior:** Allowed operations are limited to documented
  public reads; mutation, intake, approval, publication, provider, and admin operations
  are absent or explicitly rejected.
- [ ] **AC-607.4 — Safety semantics:** Contract tests prove no client output upgrades an
  unresolved result, infers intent, exposes private data, or treats a candidate relation
  as a published accusation.
- [ ] **AC-607.5 — Failure behavior:** Missing, stale, tampered, incompatible, oversized,
  slow, or malformed API data fails closed with the documented error and no fabricated
  record.
- [ ] **AC-607.6 — Deterministic CI:** DP-602 runs client contract tests, dependency and
  license checks, secret/private-data scans, and a local mock-server suite without a
  provider, credential, remote, or paid call.
- [ ] **AC-607.7 — Clean-clone proof:** A detached clean clone installs the selected
  client/tool from pinned inputs, exercises the local mock API, runs the public fixture
  path, and leaves no generated source or secret in the repository.
- [ ] **AC-607.8 — Version/deprecation proof:** Client metadata records the supported
  public API range, generated source/OpenAPI version, and behavior for a deprecated or
  incompatible endpoint. A client release cannot override DP-403's sunset policy.
- [ ] **AC-607.9 — Licensing proof:** Every client dependency, generated artifact,
  example, and notice has an DP-603 inventory row and compatible license evidence;
  unknown rights block the client rather than being assumed.
- [ ] **AC-607.10 — Migration/contract safety:** No client-specific database migration is
  introduced. A public contract change follows DP-105/DP-403 migration and compatibility
  policy, with old clients held or deprecated explicitly.
- [ ] **AC-607.11 — Optionality:** If no safe, useful client surface is justified, the
  accepted outcome is “do not build” with the decision receipt; no placeholder SDK/MCP
  or skill is shipped.
- [ ] **AC-607.12 — No external publication:** This specification does not publish an
  SDK, MCP endpoint, skill, remote, registry artifact, API URL, or release.

## Validation / proof

The selected implementation must provide a local contract matrix covering:

- manifest and valid resource reads;
- empty collection, bounded pagination, invalid cursor, and `404`/`503` errors;
- unresolved, correction, reply, relation, and ContentAudit public examples;
- missing/stale/tampered/incompatible projection;
- unsupported method and mutation rejection;
- retry/timeout/size-bound behavior; and
- safe logging with no private data.

The receipt must include the standard repository checks:

```text
python3 -m compileall -q poc tests
PYTHONPATH=poc python3 -m unittest discover -s tests -v
PYTHONPATH=poc python3 -m dichiarazioni_pubbliche.benchmark
git diff --check
```

It must also include:

- an OpenAPI/schema compatibility test and generated-client diff check, if applicable;
- a local mock HTTP server test with no network/provider calls;
- a detached clean-clone install and exercise receipt;
- DP-603 license/notice validation; and
- the DP-601..DP-607 ticket completeness/collision audit.

If the client is runtime-affecting, MiniPC read-only proof is required for the selected
integration. A Mac-only mock result is not public or production proof. No hosted client
or external publication is part of this ticket.

## Documentation, data, and migration impact

- Add client documentation only after the API/OpenAPI contract is stable; link to
  DP-105, DP-402, and DP-403 rather than duplicating field definitions.
- Add a client fixture or generated artifact to DP-603 before distribution, with exact
  version/license/notice evidence.
- Do not add a database migration. A public contract change is owned by DP-105/DP-403
  and follows the normal compatibility/deprecation process.
- Do not edit `PLAN.md`; this remains a FUTURE M6/client decision.
- Do not publish a client, registry package, MCP endpoint, skill, or API URL from this
  specification.

## Blocked conditions

Keep the ticket `FUTURE`/`BLOCKED` or classify client work incomplete if:

- DP-105 has not ratified the public schema and compatibility vocabulary;
- DP-402 has not proven the stable read-only HTTP contract;
- DP-403 has not accepted OpenAPI, examples, and deprecation behavior;
- M3 privacy, rights, or legal gates block the data/API surface;
- the owner has not chosen one client surface and its maintenance owner;
- a client would require private data, provider/LLM calls, writes, publication authority,
  or an unapproved deployment;
- dependency/license evidence, clean-clone installation, or security tests are missing;
- the API would need a breaking change to accommodate a client; or
- the requested work would publish/register an SDK, MCP server, skill, remote, or release
  before the gate and owner authorization.

Pending API contract closure, owner selection, optional client implementation (if chosen),
mock/contract tests, clean-clone proof, MiniPC proof where applicable, license inventory,
and the DP-601..DP-607 ticket audit. The accepted no-build outcome is valid when no safe
client surface is justified. No client or external publication is claimed here.
